# Knowledge Village — storybook UI demo

Standalone, interactive mobile/tablet demo of the Knowledge Village town-building screen.
Open `index.html` in a browser (no build step, no server needed).

Files: `index.html`, `style.css`, `app.js` (plus this README). `IMPLEMENTATION_BRIEF.md` is the unchanged handoff brief.

## Safety / isolation
- No network requests, no external fonts/scripts/images, no secrets, no analytics.
- **Storage (v8):** exactly one `localStorage` key, `kv-storybook-demo:v8` (plus a `…:damaged` copy only if a save could not be parsed). The main app's storage is never read or written; no cookies, no `sessionStorage`. If storage is blocked, the demo works in memory and says so in the parent panel.
- Rewards (v8) come only from correctly answered questions — see the v8 section. The old "press a button, get resources" study buttons are gone.
- Nothing outside `storybook-demo/` was touched.

### What changed (only `index.html` cache-bust strings, `style.css`, `app.js`, this README)
- **Multiplication track — 42 original generators** (`KVLearn.MULT_TEMPLATES`, kept apart from the 28 v8 add/subtract templates): (a) `groups` — equal groups / repeated addition (5); (b) `expr` — multiplication symbol, story ⇄ expression (4); (c) times tables — 3 generators for each of 2, 5, 3, 4, 6, 7, 8, 9, 1 (symbol, story, missing number; 27); (d) `mword` — fantasy-village word problems incl. two-step add / subtract and "which problem is multiplication / which expression" choices (6). Products are ≤ 81; early stages use factors 2–5. Order convention **「1つ分の数 × いくつ分」** (3こずつ 4さら = 3 × 4); the swapped expression is never offered as a wrong choice. Wrong numeric choices are typical slips (added instead of multiplied, one group too many/few, off by one). Equal groups are drawn with plain DOM dots (`.q-groups`), no canvas.
- **Mastery model per topic** (add vs subtract word-problem types, groups, expression, each table, multiplication word problems): progress = (first-try-no-hint correct + ½ other correct) / 5, scaled by accuracy; errors and hints are counted; `last` day per topic drives spaced review (3 days, 7 once mastered ≥ 80 %). Stage unlocking is rule-based: a topic opens when the parent's unit reaches it **or** its single prerequisite reaches ≥ 40 % (groups → expr → 2 / 5 / word problems; 2 → 3, 1; 5 → 4; 3 → 6; 4 → 7; 6 → 8; 7 → 9). Add/subtract is always open, so the child is never locked out.
- **Question mix:** ~60 % current unit, ~30 % weak/due review (falls back to earlier unfinished topics, then current), ~10 % ahead (next unit, only when its prerequisite is really met; an empty pool falls back to the current unit). "ふくしゅう多め" mode = 40 / 55 / 5. Never repeats the last template back-to-back when avoidable; picks weaker topics more often.
- **Parent section** (inside the closed "おうちの方へ" panel, behind a small arithmetic check, cleared when the sheet reopens): school unit (addsub / かけ算のはじまり [default] / 2・5のだん / ほかのだん / かけ算の文章題), mode (ふつう / すこし先へ / ふくしゅう多め), a next-up preview worded as a rough 2–4 week suggestion, **not** a school schedule, and per-topic progress bars. Settings live in `learn.settings` inside the existing single key `kv-storybook-demo:v8`. Changing them never resets progress, rewards or the village. Children only see the subject choices and the next question.
- **Rewards:** unchanged correctness economy — wrong/unsolved = 0 resources, 0 points; full for first-try without hint, 60 % with hint or one miss, 30 % after two misses. New: harder topics (tables 6–9, multiplication word problems, the two v8 "reverse" topics) solved first-try without hint earn **+3 🪵 and +2 開拓点**. New guard: every generated question id (`template:seed`, last 300 kept, survives a stats reset) rewards at most once, on top of the pending-question persistence, `paid` flag and 30/day cap.
- **Migration:** v8 saves load unchanged (`learn.v` 1 → 2 in memory): solved counts, per-topic counts, daily guard, pending questions are kept; new fields (`err`, `last`, `settings`, `seen`) default to zero/empty and are validated/clamped; **no counts are moved to multiplication topics and the village is untouched**. Storage key and save version are unchanged.
- No new frame loops, no canvas or ground-layer change, no network, no dependencies.

### What changed
- **Study sheet = real questions (`KVLearn` at the top of `app.js`, pure logic, no DOM).**

  - **Japanese:** 10 curated kana / kanji-reading / short-sentence items. **English:** 10 word–picture / meaning items. Pictures are system **emoji (placeholders)**. **No speech recognition and no audio** in either subject (stated in the sheet).
  - One question at a time, large (≥ 44 px; choices 56 px) targets, 💡ヒント (never contains the answer), wrong choices grey out and cannot be re-tapped, the 2nd miss shows the hint automatically, the 3rd miss shows the worked answer (no reward, warm text, "next" is always available — no dead end). - **Rewards only for a correct answer.** Same base amounts as before (算数 🪵12, 国語 📚3+🪵2, 英語 🌍2+🪵2, each 開拓点+10), scaled by how it was solved: no hint & first try 100 %, hint used or one miss 60 %, two misses 30 % (each resource at least 1). Three misses = no reward. Guards: `answer()` sets `done` before granting; `claim()` pays each result once (`paid` flag, also at boot for a result decided but not yet paid); a pending question is saved and **resumed after reload or leaving the sheet** (misses/hints are kept, so it cannot be re-rolled); math: 30 rewarded questions per local day, Japanese/English: each item rewarded once per local day — beyond that it is labelled "れんしゅう" with no reward and no unlock credit. "Reset learning stats" keeps the daily counters and open questions. Limit: the device clock can be changed to reset the daily counters; this is a local prototype, not a security boundary.
- **Unlocking uses verified solved counts** (`KVLearn.NEED`: 算数 4, 国語 3, 英語 3 rewarded-correct answers). `S.skills` is only a mirror of those counts. Old builds persisted nothing, so there is no old button-press count to migrate and **no mastery is granted from it**. Buildings already placed are never removed if a count is later reset.
- **Progress tracking & parent panel** ("おうちの方へ" in the study sheet): questions, correct, first-try-without-hint, hint rate, addition vs subtraction accuracy, per-topic counts, last 5 results. Small samples (< 10 answers) say so instead of rating the child. Optional **export (JSON of learning stats only)** via a local file download and **reset of learning stats only** (two taps). No names, no identifiers, no network.
- **Persistence & migration.** Village (land size, resources, 開拓点, buildings, stored buildings) and learning state are saved to the single namespaced key (debounced, plus on `pagehide`). On load every field is validated and clamped; unknown fields are ignored; buildings that do not fit (unknown type, outside land, overlapping tiles) go to the stored inventory rather than being deleted; a save from a newer version is left untouched (saving is disabled); unparsable data is copied to `…:damaged` and defaults are used.
- **Performance:** the cached ground layer, sprite atlas and loop are untouched. The learning UI is plain DOM (no canvas animation, no fetches, no timers beyond a 600 ms save debounce). Main app untouched; water flow remains out of scope.

## v7 changes (from `V7_FEEDBACK.md`) — gentle animated river only
**Verification status — read first:** `node --check` was **not run** (the sandbox required approval that was not granted), and no browser or phone was available. The code is re-read by hand only. Smoothness on the owner's Android device, and whether the flow looks right, **need the owner's confirmation**. Run `node --check storybook-demo/app.js`, then open `index.html?perf=1`.
- **Cause of the frozen water:** the river and waterfall are painted into the cached ground layer at `T = 0`. v7 leaves that alone.
- **New separate layer (`drawRiver`, section 6b of `app.js`).** After the ground blit and before buildings / scenery sprites it strokes a bounded set of short highlights: 10 streaks on phones (fast mode), 18 on desktop, in three `Path2D` strokes (white, white, faint blue ripple lines). They travel **downstream along the sampled river centreline** (source = waterfall, flow = towards the viewer) and are shrunk to nothing at the ends of the river so they never pop. The waterfall gets three sliding dashed trickle lines and two expanding pool ripple rings. No gradients, no offscreen bitmaps, nothing in land / trees / cliff is repainted.
- **Cached per ground build:** centreline lengths, streak seeds and the bridge keep-out box live on the ground layer (`stat.river`, from `prepRiver()`), so they follow the same invalidation as the ground (size, viewport, DPR) and nothing else. Selecting, building, moving, studying and expanding do not rebuild the ground because of the water. The highlights use the same base→live camera transform as the ground blit, so they do not drift while a sheet shifts the camera.
- **Bridge stays on top:** the highlights are clipped (even-odd) around the bridge's screen box (deck, rails, lanterns), and buildings / scenery are drawn after the river anyway. The box is a rectangle, so the water shimmer gaps slightly wider than the deck there: a deliberate simplification.
- **Rate and pausing:** river ticks run at ~15 fps (fast) / ~20 fps (rich). Between ticks the loop only polls. Nothing runs while the tab is hidden. With `prefers-reduced-motion`, or when the Battery Status API (where it exists) reports ≤15 % and not charging, motion is paused and one still frame of highlights is drawn. There is no general "low-power mode" web API, so iOS / Android battery-saver is **not** detected. A river-only tick does not advance the clock for clouds / leaves, so their 8 s idle stop is unchanged. Trade-off: a visible tab now draws ~15–20 times a second even when idle, where v6 fast mode drew none. That costs battery; measure it.
- **`?perf=1`** adds `river <avg ms> avg <worst ms> worst (<draws> draws)`, the time spent in `drawRiver` only.
- Not touched: scenery, buildings, learning, modal, map, bridge / crossing logic, saves, any file outside `index.html`, `style.css`, `app.js` and this README (`index.html` and `style.css` needed no change).

## v6 changes (from `V6_FEEDBACK.md`) — performance redesign + river crossing
**Verification status — read first:** written and re-read by hand only. In this sandbox `node --check`, a headless browser and any phone were **not available / not approved**, so the syntax, behaviour, frame times and memory figures below are **unverified and unmeasured**. No claim is made that it reaches <16 ms or <33 ms on a mid-range Android. Do this before relying on it: `node --check storybook-demo/app.js`, open `index.html?perf=1` on a real phone and read the overlay, then try `?quality=rich` / `?quality=fast` to compare.

### Performance (what is actually different from v5)
1. **Painting is separated from interaction.** One *ground layer* (meadow, river, bridge, road, all scenery that no building can overlap, foreground plants, vignette) is painted into an offscreen canvas **only when terrain changes**: land size or viewport / DPR (`staticSig()` contains nothing else). Taps, selecting, long-press lift, build / move / store, undo, the build shop, the study sheet and the placement bar do **not** rebuild it (v5 rebuilt it on every building change and whenever a sheet moved the camera).
2. **No vector trees at runtime.** Trees, bushes, rocks, stumps and flower patches (including the painted backdrop forest rows) come from one **sprite atlas** (kind × 3 variants × size bucket on a ×1.2 ladder). They are drawn once and reused across stages; only a resize clears the atlas (and a 28 MB guard clears it between builds). Even a 64-tile forest is a few dozen bitmaps blitted once per terrain change.
3. **Buildings are cached bitmaps.** Each building type is vector-drawn once per zoom into a small sprite; a frame blits it (move ghost and hover preview too). Consequence: the animated bits (chimney smoke, flag waving, butterflies, telescope sway) are **frozen** — a deliberate trade, performance over decoration. Shop thumbnails are drawn once, one per tick, then copied.
4. **No per-frame O(N²).** The painter's order (`depthSort`, still the footprint topological sort) runs only when the building set or the ground layer changes (`ensureOrder`), on buildings plus the few scenery objects inside a building's possible painted reach (≈ a few dozen). Per frame it is a plain array walk.
5. **Camera never repaints.** The base camera used for the ground layer ignores sheets / bars. A sheet only moves / scales the finished image (`affine()`), eased over a few frames of 2–3 blits. Layout, resize (debounced 180 ms) and viewport changes are the only other rebuild triggers.
6. **Expansion = image cross-fade.** `doExpand` freezes the current scene ("before") into a reusable offscreen layer, changes the land, and on the *next* frame builds the new ground layer once and composes "after". The 1.1 s animation is then two scaled `drawImage` calls (the cameras and both images are interpolated; the backdrop forest cross-fades too) + one pre-rendered bloom sprite. Cleared-tree ghosts and per-tile flashes were removed. Taps are ignored while it runs. `prefers-reduced-motion`: no animation, one rebuild.
7. **Fast mode (default on phones / coarse pointer / ≤4 GB or ≤4 cores)**: canvas backing store at **1x** (CSS scales it), sky + far hills flattened into one backdrop image, no ambient clouds / leaves, half the meadow tufts, ~30 % fewer low plants, fewer foreground plants and sparkles, no render loop on bare finger movement. Idle page = **zero** animation frames. Desktop gets "rich": up to 1.5x and gentle ambient clouds / leaves for 8 s after a touch. Force with `?quality=fast` or `?quality=rich`. (There is no in-app toggle.)
8. **Animation stops when idle and when hidden** (`document.hidden`, no rAF). Highlight pulses run at ~20 fps only while something is selected / previewed.
9. **`?perf=1`** overlay (mobile-safe, bottom-left): quality mode, fps of frames actually rendered, last / average / worst frame callback ms, ground rebuild count and its last duration, order rebuilds, canvas size @DPR, sprite counts and a rough memory estimate (layers + atlas; an estimate, not a measurement). `KVDemo.stats()` returns the counts for tests.

Known costs: the one-off ground build on a size change or resize still paints the whole meadow, river and ~hundreds of sprite blits in a single frame — expect it to be the slowest moment (`ground rebuilds (…ms)` in the overlay shows it). While a sheet is open on a landscape phone the cached image is scaled (slightly soft) until it closes.

### River and expansion
- **The river is a world feature, not a plot decoration.** It follows `riverGX(gy)` (about `gx = −1`, bending to the north-west upstream where the waterfall is) in *grid* coordinates. Previously it was placed relative to the plot and so always ran away from it; now the plot grows toward it: 4×4 and 5×5 leave forest between, 6×6 reaches the meadow edge to the bank, 7×7 and 8×8 sit right next to the water. The water stays scenic: scenery keeps off the river and bridge, and it is never covered with grass.
- **Footbridge + far bank at 7×7 (49 tiles).** A plank bridge with posts, rails and lanterns spans the two cells `(−2,2)`–`(0,2)`. Opposite the plot, a **far-bank meadow of real buildable cells** appears: 3×4 = 12 cells at 7×7, 3×5 = 15 at 8×8 (HUD: `土地49マス＋対岸12`). The expand sheet announces the bridge in advance and the preview highlights the bridge deck and the new cells in gold.
- **One rule set.** `inLand()` (plot ∪ far bank) feeds tap → tile mapping, placement, the move/long-press flow, the grid overlay and the scenery keep-out polygons, so hit-testing and restrictions agree. River and bridge cells are *not* land: nothing can be built in the water or on the bridge. A building cannot straddle the river (the gap is 2 columns). Collision between buildings (tile footprint → bounding box → silhouette SAT) is unchanged and applies across the river too.
- **Meadow.** The clearing is the union of the plot clearing and a smaller far-bank clearing (same wobbling soft edge), clipped together so there is no seam; trees beyond it, stumps where the outline swallowed trees. Existing buildings keep their positions at every expansion; the camera widens to fit the far bank.
- **Restrictions / honesty.** The far bank is a fixed rectangle, the bridge is a fixed one-cell footbridge (no walking character, no path-finding — "reachable" means "available to place buildings"), and the river itself did not animate in v6 (cached still; v7 adds a separate highlight layer, see above). The bridge is a 7×7 *unlock*, not a separate purchase. Nothing here has been seen running; far-bank framing at 360 px width is an estimate by calculation (cells ≈ 28–30 px) and needs a look on a phone.

### Unchanged / preserved
Study, resources and buttons, grid only while editing (build / move), long-press lift → destination tap → cancel (「やめる」 / Escape / tapping the same spot / second finger / `pointercancel` / blur / hidden tab), tile-footprint + bounding-box + silhouette collision, isometric angle, shadows, foreground kept to low plants in the side strips with the centre free (now also kept off the far bank and bridge), dialogs (one modal at a time; toast / sheet / placement bar step aside). No storage, network or external assets. Art is original procedural drawing; **no claim is made that it matches any supplied raster screenshot.**

## v5 changes (from `V5_FEEDBACK.md`) — smartphone performance
**Verification status — read first:** written by reading only. The sandbox did not allow running Node or a browser (`node --check` required approval that was not granted), so syntax, behaviour and the actual frame-time gain are **unverified and unmeasured**. Run `node --check storybook-demo/app.js`, open with `?perf=1` on an Android phone and compare against v4 before relying on this.

1. **No full world redraw per frame.** Ground (meadow, stream, road) and all scenery that no building can overlap are painted once into a cached offscreen layer, then blitted. The cache signature is: viewport size, DPR, usable area, camera (zoom/pan), land size, expand-preview state, and every building's id/type/position — so it is rebuilt on resize, expansion, build/move/store/undo. Animation ticks never rebuild it. While the camera eases or the expand effect runs, the scene is painted live in the original layer order, then re-cached on settle.
2. **Event-driven loop.** `requestAnimationFrame` is requested only when something is dirty, the camera/grid/effects/long-press ring animate, a pulsing highlight is shown (~30 fps), or for ambient motion (clouds, leaves; ~15 fps) which stops 8 s after the last interaction. Nothing runs while the tab is hidden; `prefers-reduced-motion` has no ambient or pulsing redraws at all. Trade-off: the cached stream/waterfall is a calm frozen state (no flowing dashes).
3. **No per-frame O(n²) sort.** Scenery is sorted once at start (point objects). Only scenery whose painted box touches a building (or is marked for the next expansion) is depth-sorted, with the buildings, by the existing footprint-based topological sort (n is small). The sorted list is cached with the static layer, so building overlap/draw order and hit-testing are unchanged.
4. **Render resolution.** DPR is capped at 1.25 on phones / 1.5 elsewhere and limited by a ~1.5 MP pixel budget. Sprite and tray-thumbnail DPR follow the cap. The vignette gradient and foreground placement list are cached.
5. **`?perf=1`** shows a small local overlay: fps, average draw ms, canvas size @DPR, cache rebuild count. Hidden otherwise; nothing is stored or sent.
6. Unchanged: stage counts 16/25/36/49/64, forest retreat, meadow, resources, placement/collision (tile footprint + painted box + silhouette), long-press lift → destination tap → cancel, grid only while editing, dialog fixes, no storage/network.

Long messages were shortened.
2. **Land expansion = clearing the forest.** The forest is a fixed set of world-space trees / bushes / rocks (`WR0..WR1`, well past 8×8). Each object has a clearing distance from the plot edge that grows with every expansion (trees ≈0.9 → 2.6 tiles, bushes ≈0.35 → 1.6), so the ring around the plot empties and the edge withdraws: 16 → 25 → 36 → 49 → 64 tiles. The painted backdrop forest is rebuilt per stage (front rows removed first, rest climbs toward the horizon, side trees thin out and move outward) and cross-fades. The lawn halo widens and a dirt road gets wider. In 土地を拡張, trees that the next step will clear glow gold.

4. **Placement / overlap.** `visualConflict` now checks, in a scale-free projection: projected tile-footprint diamonds, then painted bounding boxes (broad phase), then the exact painted silhouettes (SAT). Draw order is a topological sort by footprint rectangles (wholly-left / wholly-behind), with x+y only as a tie-break — replacing the plain x+y sort, which is wrong for large buildings beside small ones. Moves use the same check (the mover ignores only itself).
5. **Long-press move.** Unchanged flow (hold 500 ms → tap destination), plus pointer capture, cancel by tapping the building's own spot, 「やめる」, Escape, mode buttons, or hiding the tab.
6. **Foreground.** Foreground plants live only in the outer 15% of each side, are capped in size, avoid the plot outline, and thin out as land grows; the centre stays clear. Trees/bushes are drawn from cached bitmaps to keep the denser forest cheap.
7. **Art.** More forest depth and a road/clearing; still original procedural drawing. **No claim is made that it matches any supplied raster screenshot** — none is in the repo and no comparison was done.

## v2 changes (from `V2_FEEDBACK.md`)
1. **No visual building collisions.** Placement is refused when the *painted* shapes touch, not only when logical tiles do. Each building has a screen-space silhouette (convex hull of walls, roof overhang, ridge, chimney/cupola/mast/flags, doorstep and props) computed in a scale-free projection; two silhouettes must not overlap (separating-axis test) in addition to the tile-footprint test. The same silhouette is used for tap hit-testing. Roofs and props were pulled back inside their own tile so side-by-side buildings are possible; draw order is depth-sorted. An invalid preview is drawn red (footprint, outline, the blocking building) with a shake and a reason in the action bar; the OK button stays disabled, so no resource is spent and nothing moves. Trade-off: because tall roofs project upward on screen, two houses on tiles that are directly adjacent along the "front/back" axis are refused; they fit side by side along the diagonal or with a gap.
2. **Long-press move.** In browse mode, press a building for 500 ms (a progress ring fills) to lift it, then tap any valid tile to move it (undo toast offered). A short tap only selects. A visible 「やめる」 button (and Escape) cancels; drifting more than 10 px, releasing early, a second finger, `pointercancel` (browser scroll/gesture takeover), blur, scroll or tab switch cancel the pending press. Invalid targets show red feedback and a reason and keep the building lifted.
3. **Clear editable land.** Scenery is only drawn when its painted bounding box does not touch the plot outline; trees stand behind/beside the plot only, the front uses low bushes/rocks/flowers, and foreground dressing is limited to the two bottom corners. Side framing trees are sized from the screen width so they do not climb onto the plot on a phone.
4. **Richer illustration** (all procedural Canvas, no assets): layered, shaded and blossom/fruit-dotted trees, flowering bushes, faceted mossy rocks, petalled flowers, hazy far cottages, luminous meadow with bokeh and warm flowers, dappled lawn light with a leafy lip, pointed-picket wooden fences with post caps and shadows, stream lily pads/cattails/glints, a faint rainbow in the waterfall mist, and buildings with clapboard, stone joints, timber corners, shutters, curtains and warm window glow, shingled roofs, gable timbers, doorstep and wreath.

## What works
- **Normal view shows no grid** (the grid is logical; the ground is a continuous meadow). The tile grid (semi-transparent, orange tint on occupied tiles) fades in only in 建てる / 建物を移動 modes.
- **Build (建てる FAB):** pick a building in the tray, tap a tile to preview (green = OK, red = blocked), then OK (or tap the ghost again). Correct footprint, collision against land edge and other buildings, currency deducted, undo toast. Buildings put away earlier appear in the tray as "しまってある ×n" and are placed for free.
- **Move (建物を移動 button):** tap a building, tap a destination, confirm. Invalid destinations are shown red and blocked; the building is never lost. Undo toast. (Long-press in browse mode is the faster path, see above.)
- **Store (建物をしまう):** tap a building → confirmation dialog → stored (not destroyed) with undo.
- **Selection:** in the normal view, tapping a building highlights it and shows 移動 / しまう chips; pressing and holding lifts it for a move.
- **Expand (土地を拡張):** 4×4 → 8×8 for 開拓点 20/35/50/70; existing buildings stay put, the camera re-fits, and the new ring is previewed in gold.
- **Simulated rewards (学ぶ FAB):** 算数 → 🪵+12, 国語 → 📚+3 🪵+2, 英語 → 🌍+2 🪵+2, each +10 開拓点. Studying each of 算数/国語/英語 twice unlocks the multi-subject buildings (図書館, 天文台, 国際カフェ, 貿易商店, 交流ホール).
- Layout fills the viewport (`100dvh`, safe-area insets), canvas scales with devicePixelRatio, 44px+ touch targets, `prefers-reduced-motion` respected. Escape returns to the normal view.

## Known limits
- On a narrow phone the full 8×8 plot is small (~30px tiles); the view auto-zooms to fit the current land size but there is no manual pan/zoom.
- Buildings are tapped via their painted silhouette (convex hull, slightly conservative around chimneys/flags), which is also what keeps them from visually overlapping; this makes some adjacent-tile placements impossible by design.
- `window.KVDemo` exposes in-memory state/helpers for automated checks only.
